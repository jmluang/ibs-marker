# Backend-only cloud Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** 浏览器只访问本站 API，Supabase 项目配置、SDK 调用和 access/refresh token 全部留在后端，保留现有账号、共享数据库、RLS、离线记录及原子同步。

**Architecture:** React 的同源 BFF 客户端替换浏览器 Supabase SDK。Node 使用已有绑定物理接口的受限 curl transport 调用原项目 Auth/PostgREST；注册继续使用服务端管理密钥，用户数据只使用该用户 Supabase JWT + 项目 public key。浏览器仅持 HttpOnly 不透明会话 cookie；Supabase token 加密保存于服务端私有文件，不自行签发身份 JWT。

**Tech Stack:** Existing React/TypeScript/Node, node:crypto AES-256-GCM, existing curl transport, existing PostgreSQL/RLS/RPC; no new database or migration.

## Scope and gates
- 用户已授权实现并在既有15001/域名更新；不 commit/push，不改5217、Tunnel、全局网络、供应商原生注册配置或真实用户密码/数据。
- Parent owns shared contracts, root build/dependency config, private env, integration/evidence and production runtime. Workers never read real env, use real cloud, write dist, or operate existing services.
- Pre-flight: independent plan/security review must pass before source implementation. Revision: each stream spec then quality; unresolved important issues block release. Final integration and real HTTPS acceptance required.
- Existing accounts keep exact username mapping and UUID; no forced reset. Old browser provider tokens are not imported or trusted: one re-login is acceptable; health-data IndexedDB/outbox must not be cleared, migrated across users, or auto-uploaded into another account.

## Frozen HTTP contract
Every response is no-store JSON; safe failure `{ok:false,code}` only, no provider bodies, URLs, keys or tokens. Mutations require exact allowed non-null Origin, JSON, strict fields, request limits/timeouts, per-IP/global auth rate limits. Reject cross-site fetch metadata, disallow CORS, no generic upstream proxy/path/headers/body forwarding.

- Existing `POST /api/register {username,password,inviteCode}`: same fixed registration codes, 201 `{ok:true}`; no session side effect. Client auto-login afterward using BFF below.
- Sole cookie issuance: `POST /api/auth/bootstrap {}` returns `{ok:true,user:null|{id,displayName},authRevision:string}` and sets one anonymous opaque SID only if no valid context cookie exists. An existing valid context returns current verified state without Set-Cookie. All other endpoints NEVER set/rotate/clear SID cookies. Browser holds origin-wide exclusive Web Lock `ibs-marker-bff-bootstrap` across session probe, bootstrap, complete body read and confirming session probe; no other tab may authenticate before this handshake completes. Cancellation must not release this lock while a bootstrap response can still set a cookie; bootstrap fetch is not raced with a cancellation promise. If Web Locks is unavailable, fail closed with explicit browser-support notice rather than unsafe concurrent bootstrap. Test two no-cookie tabs: second handshake cannot issue its bootstrap or begin B authentication before the first bootstrap response fully completes.
- `GET /api/auth/session`: existing context only; `{ok:true,user:null|{id,displayName},authRevision:string}`; missing/expired/unknown context returns 428 `SESSION_CONTEXT_REQUIRED` with NO Set-Cookie. Foreign Origin/cross-site fetch metadata rejected. Transient upstream errors 503, not false logout. authRevision is an unpredictable non-provider generation nonce for both anonymous/authenticated context; every auth state change advances it, refresh does not.
- `POST /api/auth/prepare {authRevision}`: compare-and-swap against current context in store transaction; stale revision gives 409 `SESSION_CHANGED` with no change. Success clears previous auth, advances revision and attemptId; returns `{ok:true,authRevision:string,attemptId:string}`. No cookie issuance. Client captures both returned values before issuing login.
- `POST /api/auth/login {username,password,attemptId,authRevision}`: server maps username, normal password grant with public key, verifies returned identity through Auth `/user`; commits tokens only if exact revision+attemptId still current after all awaited operations. Success advances revision again and returns `{ok:true,user:{id,displayName},authRevision:string}` without provider tokens/cookie changes. Invalid credentials 401 `INVALID_CREDENTIALS`, cancelled/stale revision 409 `SESSION_CHANGED`, rate 429 `RATE_LIMITED`, provider/network transient 503 `AUTH_UNAVAILABLE`, malformed 400 `INVALID_REQUEST`/`INVALID_USERNAME`/`INVALID_PASSWORD`.
- `POST /api/auth/logout {authRevision}`: compare-and-swap the captured revision, atomically advance revision/clear auth and durably commit before any provider awaits; stale revision gives 409 `SESSION_CHANGED` and MUST NOT touch B. Returns `{ok:true,authRevision:string}` only after durable local logout. Any upstream revoke uses captured old user token/scope=local; its failure/completion cannot clear newer B. Keep stable anonymous cookie. Cancel and offline-logout retries carry only the revision being cancelled; never unconditionally revoke the latest server session.
- Both sync APIs require `X-Auth-Revision` matching the exact current authenticated generation. Reject old A's queued request with 409 `SESSION_CHANGED` before using new B's JWT, even with shared stable SID cookie. Capture user JWT + revision before awaiting; recheck after refresh and upstream responses; an old A failure must not revoke newer B. In-flight A already at Supabase stays scoped to A's captured JWT.
- `GET /api/sync/pull?cursor=<nonnegative safe integer>&limit=<1..100>`: authenticated and version-bound, fixed select/order/filters for tracker_changes only; returns `{ok:true,rows:ChangeRow[]}` matching existing engine.
- `POST /api/sync/push {operation:OutboxOperation}`: authenticated, strict validate canonical existing operation fields/snapshots, forward only fixed tracker_apply_change RPC fields; returns `{ok:true,result:PushResult}`. User-supplied owner/user/JWT/key/URL fields rejected. Preserve change IDs, versions, conflict/tombstone and duplicate-meal semantics. Permission/auth errors 401/403, known uniqueness code 23505 retained through fixed safe code only; no raw SQL/provider detail.

## Session security and lifecycle
- 256-bit cryptographic random cookie SID; store hashed SID only. HTTPS production cookie `__Host-ibs_session`, Secure, HttpOnly, SameSite=Strict, Path=/, no Domain. Plain cookie allowed only explicitly configured loopback HTTP fixtures. SID never in JSON, localStorage, URLs or logs.
- Bounded encrypted session file under ignored private directory (0600; atomic replacement). Parent creates one unprefixed private SESSION_ENCRYPTION_KEY automatically if absent; never expose it or require user to manage another secret. CLI refuses unsafe/missing runtime key; tests explicitly inject memory store/fake key, no env reads. TTL/capacity + bounded parsing. Corrupt/undecryptable store fails closed, never overwritten silently. ONE single-process store writer serializes all contexts: conditional state mutation + encrypt/atomic replace + publish is a single ordered transaction, never async read/modify/write snapshots outside it. Login/refresh successes publish only after durable commit; disk error returns 503 and poisons store fail-closed, never claims success. Provider HTTP runs outside writer; final commit rechecks revision in transaction.
- Context cookie exists before asynchronous login. Prepare advances per-context auth fence, login checks it after provider grant/user validation and persistence; CAS logout/cancel/prepare prevent late A from authenticating or invalidating newer B. All operations consult current context identity, not client IDs. Refresh singleflight keyed by context+authRevision; persist rotated token before returning/using it and recheck identity/revision at commit. Definitive invalid refresh may revoke only matching captured revision; network/5xx retains session and returns 503. Use Auth `/user` for verification; never trust decoded unverified JWT/client user.
- Frontend retains epoch/AbortSignal, namespace fencing and native fetch receiver. Logout/cancel locks UI and stores an auth-lock/pending-logout marker BOUND TO CAPTURED authRevision before network/cleanup. On reload, retry only that revision; if server has newer B, discard stale retry without logging B out. Fresh login clears only applicable old lock; stale A cannot overwrite newer B metadata/lock. Storage write failure is reported, never claims durable logout, and disables cached offline-identity restore when storage durability probe fails. Never store provider tokens. Persist minimal previously verified identity/revision for same-user offline shell only; cached identity is NEVER server authorization. Cross-tab storage/BroadcastChannel changes lock previous namespace immediately; transport captures authRevision, never mutable newer identity getter. Treat 409 SESSION_CHANGED as auth/identity failure, retaining outbox.
- Clear only known legacy auth keys when safe; do not enumerate/delete unrelated localStorage or any health records. Existing offline/queue/conflict behavior remains.
