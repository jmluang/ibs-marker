# Refresh navigation and session recovery — bounded repair plan

Goal: normal external entry/query-string refresh always renders the public application shell; existing valid login survives normal refresh and browser reopen within the existing server-session lifetime; transient verification outages do not masquerade as invalid credentials.

## Verified failures
- Public domain direct GET / = HTML200; /?x=1 and /index.html?x=1 = JSON404 INVALID_REQUEST. Actual Chromium external link into / = JSON403; reloading that page remains JSON403. server/app.ts globally rejects cross-site metadata before its public static route.
- Exact raw req.url static lookup also rejects page queries. Static HTML currently awaits provider readiness and may turn into JSON503; SW returns HTTP-error/JSON navigations directly and skips query navigation entirely.
- Isolated controller tests proved AUTH_UNAVAILABLE/503 sends an existing unlocked identity to login with no recovery entry; an ordinary data FORBIDDEN/403 creates a durable identity lock even if Auth session remains valid.
- Bootstrap cookie has no Max-Age/Expires; encrypted server context itself already has a 30-day default lifetime. This alone does not explain ordinary same-origin refresh.

## Scope
No account/password changes, no health-record edits, no DB migrations, no new provider/project, no commits/push, no edits to unrelated services/Tunnel/5217. Keep provider secrets/tokens entirely server-side, fixed APIs, user JWT/RLS, authRevision/CAS, pending-logout and failed-auth offline locks. Old ambiguous locked metadata is NEVER auto-unlocked. Only new explicit sign-in clears such a lock.

## A — Public static routing, server cookie (one backend writer)
Files server/app.ts, server/bff.ts and backend tests only.
- Select only already-known immutable public assets and the / or /index.html shell (allow query for these two aliases only), without URL canonicalization/decoding/traversal normalization. A safe GET/HEAD public shell/static request may be cross-site: HTML/assets contain no user data. API Origin/fetch-site/JSON/revision gates remain strict.
- Public static snapshot no longer depends on provider readiness. /readyz and registration stay fail-closed; APIs retain actual auth checks. Dist missing/unknown navigation should get a small safe HTML error when truly navigating, not generic SPA fallback. Unknown/private/source/API/SW-mismatched paths remain rejected with their original status. Do not invent /settings History routes; app navigation is hash-based.
- All API failures remain fixed JSON and never redirect into HTML. Do not loosen SW query aliases: only validated current /sw.js?build=<active> succeeds; extra/wrong parameters still rejected.
- Add cookie Max-Age bounded to REMAINING context.expiresAt - now (never extend server lifetime). Sole Set-Cookie endpoint stays /api/auth/bootstrap. For an existing validated SID, this endpoint may reissue the EXACT SAME SID cookie with remaining Max-Age, never rotate or reset its auth/revision. No ordinary session/login/logout/refresh endpoint sets cookies. Preserve HttpOnly, Secure, host-prefix, Strict and Path. Reject unknown context outside bootstrap.
- This narrow bootstrap extension allows old session-only cookies to be upgraded safely; frontend completes it under the existing origin-wide Web Lock BEFORE any subsequent auth action. Other identity/CAS behavior unchanged.

## B — Transient recovery, permission classification, safe upgrade (one frontend writer)
Files src/cloud/**, src/cloud/engine.ts (small classify branch), CloudPanel and frontend tests only.
- Under the complete existing Web Lock, session() probes then bootstrap-reissues SAME current SID (or creates one if missing), consumes full body and confirms current session before returning. No race/cancel may release lock early. A browser without Web Locks may use an already-valid probe but must not perform unsafe bootstrap. All requests remain same-origin/no raw provider data.
- Restore may use only the previously verified, durable, unlocked matching identity cache on network TypeError OR allowlisted transient AUTH_UNAVAILABLE/503/transport-5xx, never 401/SESSION_CHANGED, never any explicit/pending logout lock. Revision-captured transport prevents old A queues using B.
- Restore itself (not only an existing engine) MUST persistently lock matching cached identity on definitive 401/SESSION_CHANGED/unknown auth-403: isolate UI first, revision/user/current-stamp CAS, never overwrite B or issue logout to B. Regression: restore invalidation followed by a newly created offline/503 controller cannot resurrect A.
- Multi-stage session() must report every successful session observation to restore (callback or typed internal outcome, NOT additional HTTP credentials). If any probe/bootstrap/confirm observed null/different user/different revision, old cache A is ineligible for fallback even when a later stage fails 503. Conditionally persist old A's invalidation while it still matches current metadata, so a later offline controller cannot resurrect A either. A successful complete handshake may accept the finally verified identity using only its own current stamp; it must never unlock a pre-existing explicit/pending logout lock or overwrite newer B metadata. Guard observation callbacks by the controller epoch. Tests cover A cache → observed anonymous/new revision/B → later 503 and then offline reload; no old A UI/queue or B logout/lock.
- Without usable cache, expose an explicit recoverable connection state/message plus a retry connection action, not invalid-password text. Online/foreground may retry restore using one in-flight recovery promise; no infinite timer or concurrent restore fan-out. Never trigger logout because verification is transiently unavailable. Existing epoch fences must guard stale recovery.
- Classify ONLY allowlisted BFF FORBIDDEN/403 and INVALID_REQUEST/403 as request/permission errors retaining identity+queue; true 401, SESSION_CHANGED and unknown/untrusted auth failures keep current durable-lock behavior. Do not remove old 401/403/409 lock regressions by broadly exempting 403. Do not grant permission or send writes with admin tokens.
- Do not auto-clear old cached.locked markers when server session is valid: they may represent explicit logout. Fresh user sign-in is the safe legacy recovery path.

## C — Navigation SW and browser regressions (one SW/e2e writer)
Files public/sw.js, SW-specific tests and e2e/** only.
- Only known UI document navigations / and /index.html (including query) get offline-shell handling. Exclude all /api/, /auth/, /rest/ and other paths first. Assets keep exact/query restrictions; never cache API bodies, credentials or error JSON.
- Known UI navigation should render network HTML if successful; for network exception or non-HTML/error response use the known cached static shell if available, without caching that response. No blanket fallback for unknown/private/API navigation, no IDB clearing, no forced skipWaiting that discards editors.
- Tests distinguish real production Node/SW acceptance from Vite shell fixtures. Add external-link then refresh, query navigation, 503 recovery while still authenticated, permission error vs revoked session, browser-close/reopen persistent cookie, and same-SID late-bootstrap/new-B safety. Preserve existing cancellation/identity/old-outbox protections.
