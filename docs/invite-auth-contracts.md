# Invite-auth shared implementation contract

**Backend-only migration deployed:** the approved replacement is `docs/plans/backend-only-cloud.md` and `src/domain/backendApi.ts`. Do not restore browser Supabase SDK/configuration. Registration semantics below remain valid; former direct-browser Auth/data implementation is superseded. The production browser only requests same-origin BFF APIs and holds an HttpOnly opaque session cookie.

**Refresh/session repair supersedes older bootstrap/static clauses:** see `docs/plans/refresh-session-recovery.md`. Only bootstrap may set cookies, but it now upgrades an existing valid SID in place with remaining-lifetime Max-Age (no SID/revision/identity/context-TTL rotation). The complete client Web Lock covers probe → bootstrap body → confirmation even for healthy existing sessions. Public known static GET/HEAD and shell query aliases are allowed for external navigation, independently of provider readiness; API Origin/auth gates remain strict. Transient verification failure is recoverable, not password failure; explicit/authoritative identity locks remain durable.

Latest user request replaces the earlier pre-provision-only/private-account UI plan. Parent owns runtime, root dependency/config files, private env and final publication.

**Single shared project/database:** every application user uses the same site-level Supabase URL/public key/database. Registration adds an Auth user to that existing project, not a project/database. Business rows remain in the shared tracker tables, isolated by owner_id/auth.uid() RLS. No customer-supplied Supabase URL, key, database password or management token is accepted by the registration API or requested in the user UI. Management PAT is site-admin setup authority only, not a per-user or permanent runtime requirement; the runtime uses its server key and public Auth-setting readback.

## Shared username module (frontend worker owns)
`src/domain/username.ts` exports `usernameToInternalEmail(username: string): string` and `isValidUsername(value: unknown): value is string`. Reject empty/non-string, malformed UTF-16, control characters, leading/trailing whitespace and UTF-8 length >30 bytes; never silently trim/case-fold/normalize. Map to `u-<lowercase hex of original UTF8 bytes>@ibs-marker.invalid`. Password is never mapped/normalized. User display name comes from admin-controlled `app_metadata.ibs_marker_username`, never display internal email.

## Browser/server API
- `POST /api/register`, JSON exactly `{username, password, inviteCode}`.
- Requires exact allowlisted non-null Origin and JSON; no missing-Origin exception.
- Success `201 {ok:true}` only after server-created account is read back as confirmed. Client then uses the same-origin BFF authentication contract; username mapping and provider password grant are backend-only. No browser `signUp`, provider SDK/key/token or Admin key.
- Registration failures return `{ok:false,code}` with a fixed allowlisted code from `src/domain/authErrors.ts`, never provider details. The invitation placeholder stays `输入邀请码`, without expected values or examples; this must not force password, username, duplicate, rate-limit or network errors to masquerade as invitation errors. No email/verification UI or guest/local bypass in configured invite mode.
- Authentication has one primary submit action (`创建账号` or `登录`) and a borderless text mode switch. Failed submission preserves the original masked inputs; only invitation-specific errors mark that field invalid. Client-side short-password validation sends no HTTP. After account creation, failed automatic login clearly reports that the account exists and returns to login rather than trapping the user in registration.
- Never reset/take over an existing username on registration. Wrong invite must not call Admin API. Account creation sets `email_confirm:true`, `app_metadata.ibs_marker_username`, and an invite-registration marker. No actual SMTP/verification sends.

## Backend module ownership
- Backend worker owns `server/**`, `scripts/start-server.mjs`, backend unit tests. Expose application factory with injectable config/transport; importing modules must not read real env or start listeners.
- `server/curlTransport.ts` exports `createCurlJsonRequest(options): JsonRequest` with options `{allowedOrigins: readonly string[], interfaceName?: string, timeoutMs?: number, maxOutputBytes?: number}`. Origins are exact HTTPS origins, required nonempty (configured Supabase origin plus `https://api.supabase.com`); default physical interface is `enp0s31f6`. `JsonRequest` accepts `{method,url,headers?,body?}` and resolves `{status,body}`. No redirects. Private headers/body go to curl config via stdin, never argv; no shell. Bounded duration/output, Abort/cancellation when supplied internally. No raw request/response/error logging; sanitize credential values.
- Runtime factory configuration includes host/port, publicOrigin, trustedProxyIPs, inviteCode, Supabase URL/publicKey/secretKey and injected JSON transport. CLI loads private .env/public .env.local, but tests inject fixtures and never read those files.
- If key/provider-registration gates are not ready, return safe preparation state and refuse registration. Explicit `/healthz` liveness and `/readyz` readiness; no secret diagnostics. Static files only from a verified build allowlist plus SW, never env/source/scripts.

Temporary operational opt-in: server-private `ALLOW_PROVIDER_PUBLIC_SIGNUP=true` permits startup without the provider-settings probe, but still requires complete URL/public key/server key/invite/Origin configuration. Only literal `true` enables it; `false` or unset retains strict readiness, and other values reject startup. The public `.env.local` cannot enable it. Temporary `/readyz` adds only `mode:"temporary-provider-public-signup"`; it does **not** claim native provider signup is closed. Native signup may bypass the application invitation while this mode is enabled; the application registration Origin/body/rate/invitation checks, confirmed Admin readback, login gate and owner RLS remain unchanged. Disable the opt-in after provider registration is made private and verified; changing this flag does not change cloud settings.

## Setup tool (setup worker owns)
- `scripts/configure-invite-auth.ts` and its own test file; imports shared transport and username helper as needed, not side-effectful server entrypoint.
- Read private env safely; use `SUPABASE_ACCESS_TOKEN` to close original signup/anonymous login and read back. May retrieve existing service key with permitted Management API read; store only `SUPABASE_SECRET_KEY` in private .env atomically without overwriting user edits. No new/pre-provisioned application accounts in this mode.
- Verify private gates with exact provider disabled errors. Negative tests use owned synthetic metadata only and clean up only provable test accounts on unexpected success, then fail. Never reopen registration on partial failure.
- Missing management authority: fail closed before cloud writes. Tokens/provider key lists stay in process memory, never reports, argv, bundle or screenshots.
